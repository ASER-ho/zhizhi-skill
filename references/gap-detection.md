# 缺口检测清单（5 类）

> SKILL.md Step 1 的详细参考。按 A-E 五类逐项扫描，评分并决定是否进入检索。

## 五类缺口

### A. 版本与兼容性
| 检查项 | 影响 | 获取方式 |
|--------|------|----------|
| 依赖库/框架版本是否明确 | 高 | Glob 搜 requirements.txt/package.json/go.mod；或 WebFetch 官方文档 |
| 语言版本是否明确 | 高 | Glob 搜 .python-version/.nvmrc 等 |
| 运行环境（OS/容器）是否明确 | 中 | 问用户或查 CI 配置 |
| 是否存在已知不兼容组合 | 高 | WebSearch 版本兼容矩阵 |

### B. API 与接口
| 检查项 | 影响 | 获取方式 |
|--------|------|----------|
| API 签名（参数/类型/返回值）是否完整 | 高 | WebFetch 官方文档 |
| 是否最新版 / 有废弃警告 | 高 | WebFetch changelog |
| 认证/授权方式是否明确 | 高 | WebFetch 官方文档 |
| 速率限制/配额 | 中 | WebFetch 官方文档 |

### C. 数据与输入
| 检查项 | 影响 | 获取方式 |
|--------|------|----------|
| 输入格式/大小/编码 | 高 | Glob 搜数据文件，Read 看样例 |
| 是否有数据样例 | 中 | 问用户或 Read |
| 数据质量（缺失/异常值） | 中 | Read 分析 |
| 输出格式要求 | 低 | 问用户，默认通用 |

### D. 领域知识
| 检查项 | 影响 | 获取方式 |
|--------|------|----------|
| 涉专业领域（医疗/金融/法律） | 高 | 委托调研 skill |
| 需要最新政策/时效数据 | 高 | 委托调研 skill |
| 行业术语/标准需确认 | 中 | 委托或定向检索 |
| 数据时效性要求 | 高 | 委托调研 skill |

### E. 现有资产（P0 优先，不联网）
| 检查项 | 影响 | 获取方式 |
|--------|------|----------|
| 项目内是否已有类似功能 | 高 | Grep 关键词 |
| 是否有工具函数库 | 中 | Glob utils/helpers |
| 编码规范（lint 配置） | 中 | Glob .eslintrc/.pylintrc |
| 测试框架与现有模式 | 中 | Glob test 目录，Grep 测试 |
| 统一错误处理/日志方案 | 中 | Grep 错误处理代码 |

## 评分标准

| 等级 | 判定标准 | 必须解决？ | 未解决处理 |
|------|----------|-----------|-----------|
| 高 | 直接影响正确性（版本不兼容/API 签名错/数据格式错/关键事实） | 是 | 检索或 AskUserQuestion，不能跳过 |
| 中 | 影响质量不影响基本功能 | 尽量 | 标注假设，用默认方案 |
| 低 | 锦上添花（格式/命名/注释） | 否 | 用默认值，不标注 |

## 评分决策流程

```
缺口是否影响结果正确性？
├─ 是 → 高 → 有现成来源可查？→ 是：必须检索 / 否：AskUserQuestion 确认
└─ 否 → 是否影响质量/可维护性？
    ├─ 是 → 中 → 尽量检索，否则标注
    └─ 否 → 低 → 默认值
```

## 复查（仅 T2，最多 2 轮）

**第一轮·遗漏**：5 类是否都过一遍？任务关键名词的版本/格式/来源都确认了？用户给的链接/文件都读了？有隐含依赖未考虑？

**第二轮·误报**：标记的缺口是否在上下文中已有答案？是否不影响当前任务？获取方式是否合理（能 Glob 解决的别 WebSearch）？

## 时效性强制（无论分级）

任务涉及**政策 / 价格 / 版本 / 法律 / 医疗 / 金融 / 新闻**等时效性信息时，一律强制检索，不凭预训练知识作答（即使 T0/T1 也要检索）。

## 前提拆解与反例（仅 T2）

动手前拆隐含前提：
1. 拆解任务与拟用方案的隐含前提（如"假设依赖已装""假设用户用 PostgreSQL"）；
2. 对每个前提列反例（什么情况下不成立）；
3. 写明结论成立的条件；
4. 无法排除的反例 → 升为缺口，进入检索或 AskUserQuestion。
