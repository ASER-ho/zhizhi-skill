# 复盘闭环（Retro Loop）

> 知止的"跨会话自改进"机制。目标是真正的闭环——**记录 → 读取 → 提取模式 → 调整行为 → 验证生效**，不是只生成复盘文本。

## 为什么需要闭环

只有"生成复盘文本"的 retro 是**日志**，不是自改进。真正的自改进必须：本次的错误能**影响下一次的执行**，并且能**验证影响是否生效**。否则漏过的缺口、错的假设会反复犯。

## 闭环五步

### 1. 记录（执行后）

T1/T2 执行完，自动把一行复盘 append 到 `~/.zhizhi/retro.md`：

```
[retro] 日期 | 任务类型 | 分级 | 漏掉缺口 | 错误假设 | 下次改进 | 生效?
```

示例：
```
2026-08-12 | 代码开发 | T1 | A-版本：没先查 Node 版本 | 假设依赖已装 | 涉运行时先 Glob 配置 | 生效
```

**自动写入**是前提（持久化才能跨会话）。路径默认 `~/.zhizhi/retro.md`，可用环境变量或用户偏好覆盖。

### 2. 读取（每次 T1/T2 启动前）

执行 Step 1 前，读取 retro 历史（最近 N=20 条）。

### 3. 提取重复失败模式

统计历史：
- 同一缺口类别（A/B/C/D/E）出现 **≥2 次** → 标记"该类别常漏"
- 同一假设模式（如"假设依赖已装"）出现 **≥2 次** → 标记"该假设常错"
- 同一路由失败（如"委托 domain-research 失效"）出现 **≥2 次** → 标记"该路由不可靠"

### 4. 调整本次行为

把重复失败模式注入本次执行：
| 重复模式 | 注入动作 |
|----------|----------|
| A-版本连漏 | Step 1 强制版本检查 |
| E-现有资产漏检 | 强制 Glob/Grep 项目内复用 |
| 委托失效 | 本次直接走降级策略，不再尝试委托 |
| 某类假设常错 | 本次对该类信息强制 AskUserQuestion |

### 5. 验证是否生效（执行后）

执行结束时对照"本次是否仍犯同类错误"：
- 未再犯 → retro 记 `生效`
- 仍犯 → retro 记 `未生效`，并评估是否需要结构性改动（如 SKILL.md 的检查项/触发词）

## 与饕餮（skill 进化）的关系

- retro 闭环解决**使用层面**的反复失误。
- 若某类失败是**方法论结构性缺陷**（改了也不生效）→ 把信号交给 skill 进化流程（如 taotie）做结构性改进，而不是靠 retro 硬扛。
