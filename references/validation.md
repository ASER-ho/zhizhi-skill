# 融合校验：方案评分、来源可信度与冲突处理

> SKILL.md Step 3 的详细参考。"知止"第二层：检索到的方案不能盲信，必须评分、校验、处理冲突。

## 方案评分：硬约束 + 任务相关维度 + 默认权重模板

**不再使用全局固定权重公式**（固定 30/25/20/15/10 是先验不是实证，对不同任务不合理）。改为三层结构：

### 第一层：硬约束（一票否决，先淘汰）

| 硬约束 | 说明 |
|--------|------|
| 版本兼容 | 与项目依赖版本不兼容 → 直接淘汰 |
| 许可证允许性 | 项目许可策略不允许（如闭源商用项目遇 GPL）→ 淘汰 |
| 安全底线 | 加密/认证/密钥/金融类：无安全审计记录或存在未修复 CVE → 淘汰 |

### 第二层：任务相关评分维度（按任务类型选模板）

| 任务类型 | 评分维度 | 权重默认值 |
|----------|----------|-----------|
| **技术库/依赖选型** | 可复用性 / 维护状态 / 安全记录 / 社区质量 / 许可证 | 30/20/20/15/15 |
| **UI 组件选型** | 设计匹配 / 可访问性 / bundle size / 维护状态 / 许可证 | 25/25/20/15/15 |
| **安全敏感（加密/认证）** | 安全审计历史 / CVE / API 稳定性 / 维护状态 / 许可证 | 30/25/20/15/10 |
| **算法/工具** | 正确性/文档 / 性能 / 维护状态 / 许可证 | 35/25/20/20 |

- 模板权重是**起点默认值**，可随任务约束调整，并在结果中**注明假设**（"权重按 X 模板，若更看重 Y 可调整"）。
- **权重是先验不是精算**：用于快速决策排序，不伪装科学精确；分差 <0.5 时优先维护性（长期风险更低）。

### 评分流程

```
1. 列出候选 → 硬约束逐项检查 → 淘汰不满足者
2. 判定任务类型 → 选评分维度模板
3. 逐项打分（1/3/5）→ 按模板权重加权
4. 选最高分；分差 <0.5 → 优先维护状态好的
5. 输出时注明所用模板与假设
```

## 工作示例：同一框架，不同语境，不同选择

证明它不是"伪精确的单公式"——**同一个库，在密码学任务里被淘汰，在 UI 任务里却可能胜出**，因为维度模板随任务类型切换。

### 语境 A：选密码学库（安全敏感模板）

> 硬约束：无安全审计 + 未维护 → 直接淘汰（哪怕 star 多）。

| 候选 | 版本兼容 | 安全审计(30) | CVE(25) | API稳定性(20) | 维护(15) | 许可(10) | 总分 | 结果 |
|------|----------|-------------|---------|--------------|----------|----------|------|------|
| `cryptography`（官方审计） | ✅ | 5 | 5 | 5 | 5 | 5 | **5.0** | **选用** |
| 某 50k★ 三年未维护库 | ✅ | 1 | 1 | 1 | 1 | 3 | **1.4** | 安全底线淘汰 |
| 某新库无审计记录 | ⚠️ | 1 | 2 | 3 | 3 | 4 | **2.4** | 不采用 |

> **教训**：star 多（50k）不救场——安全敏感语境下，无审计 + 未维护直接一票否决。

### 语境 B：选 UI 组件库（UI 模板）

> 同一个框架，但维度换成 设计匹配/可访问性/bundle/维护/许可。

| 候选 | 设计匹配(25) | 可访问性(25) | bundle(20) | 维护(15) | 许可(15) | 总分 | 结果 |
|------|-------------|-------------|-----------|----------|----------|------|------|
| 设计精美但 bundle 大 | 5 | 4 | 1 | 4 | 5 | **3.90** | 偏设计时选 |
| 朴素但轻量 | 2 | 3 | 5 | 4 | 5 | **3.55** | 偏性能时选 |

> **要点**：UI 语境里"安全审计"根本不出现；而"bundle size"在密码学语境里无关紧要。**如果任务更看重首屏性能 → 权重向 bundle 倾斜，结果反过来**。评分时把模板和假设写出来，让用户能推翻。

### 结论

固定 30/25/20/15/10 是"看起来科学"的人工先验；上下文相关的模板才是**可辩护**的——因为维度选择本身就来自任务的风险模型（加密看安全、UI 看体验），而且每个选择的依据都可追溯、可推翻。

## 验证循环（Validator→Fix→Repeat，max_retries=2）

1. **提取验证**：WebFetch 返回是否正文（非导航/广告/404/登录墙）？
2. **完整性验证**：是否含关键信息（签名/参数/版本/示例）？代码示例是否完整可运行？
3. **适用性验证**：版本兼容？依赖已装？许可允许？符合编码规范？

不通过 → 换源重试 ≤2 次；仍失败 → 标记"未验证"，进 Step 4 标注假设。**不因验证失败就降低标准强用**。

**高风险双源复核**：结论涉及生产环境 / 安全 / 合规 / 财务 / 法律时，要求 ≥2 个独立来源一致才采纳；仅 1 来源时明确标注"单一来源待验证"。

## 来源可信度：多轴判定（不单看 star）

**star 多 ≠ 正确 / 在维护 / 版本匹配 / 安全**。综合 5 轴判定：

| 轴 | 高 | 低 |
|----|----|----|
| ① 来源权威性 | 官方文档 / 厂商 | 个人博客 / 匿名 |
| ② 新鲜度 | 有明确日期且近期 | 无日期 / 多年未更新 |
| ③ 版本匹配度 | 与项目版本一致 | 面向不同版本 |
| ④ 维护状态 | 持续提交 / issue 响应 | 停滞（哪怕 star 多） |
| ⑤ 直接证据强度 | 一手（源码/官方文档） | 二手转述 |

**任一轴为关键负面即降级**：版本过时、官方已废弃、无维护（哪怕 50k star）→ 降级甚至弃用。

## 冲突处理

| 冲突类型 | 表现 | 处理 |
|----------|------|------|
| 外部 vs 原有假设 | 检索与用户信息/预训练知识矛盾 | 以外部权威来源为准，记录修正 |
| 外部 vs 外部 | 两来源说法不一 | 按多轴可信度选；同级并列呈现 |
| 版本冲突 | 不同版本行为不同 | 确认项目版本，以该版本文档为准 |
| 时间冲突 | 新旧信息矛盾 | 以较新、有日期的来源为准 |

**优先级**：官方文档 > 一手源码 > 高活跃社区 > 二手博客 > 论坛 > 无来源。

**原则**：不掩盖冲突（发现必须记录）；不擅自裁决（同级冲突并列让用户定）；记录修正（"原假设X，修正为Y，依据Z"）；标注争议。

## 交叉验证规则

| 来源组合 | 可信度 | 处理 |
|----------|--------|------|
| 官方文档 + 社区实践一致 | 高 | 直接采用 |
| ≥3 个独立来源一致 | 高 | 直接采用 |
| 2 个独立来源一致 | 中高 | 采用，标注来源 |
| 仅 1 个来源 | 中 | 采用但标注"单一来源待验证" |
| 来源间矛盾 | 低 | 并列呈现，向用户确认 |

**注意**：转载不算独立来源；有日期、版本号明确的更可信。

## 证据分级

输出时每条关键结论标注认知状态——`✅已确认事实`（有来源可验证）/ `🔶合理推断`（有依据未证实）/ `⚠️待验证假设`（无法确认）/ `❓未核实项`（没查到）。不确定就不写"确定"。
