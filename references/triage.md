# 任务分级判定细则（Triage）

> 知止的第一步是"知轻重"。本文件给出 T0/T1/T2 的具体判定依据，避免"轻任务被流程压垮、重任务漏缺口"。

## 分级总览

| 等级 | 一句话 | 流程 | 预算 |
|------|--------|------|------|
| **T0·秒答** | 无外部依赖风险，凭上下文直接答 | 不进流程 | — |
| **T1·轻流程** | 有少量未知，但低风险 | 轻量扫描 + 定向检索 | 每缺口 ≤2 轮检索 / ≤1 页 WebFetch |
| **T2·全流程** | 复杂或高风险，多缺口 | 完整四步 + 复查 + 评分 + trace + 复盘 | 每缺口 ≤3 轮检索 / ≤2 页 WebFetch |

## 判定顺序

按以下四个信号依次判定，**拿不准时升一级**（宁重勿漏）：

### 1. 任务类型

| 类型 | 默认等级 |
|------|----------|
| 琐碎修改（改 typo / 改名 / 单行） | T0 |
| 纯概念解释 / 纯数学推导 / 纯逻辑问答 | T0 |
| 简单脚本 / 单文件改动（不涉版本、API） | T1 |
| 代码开发（多文件 / 涉依赖） | T2 |
| 方案设计 / 选型 | T2 |
| 调研分析（涉时效数据 / 政策） | T2 |

### 2. 上下文充分度

| 信号 | 判定 |
|------|------|
| 用户提供完整文档/代码/链接，信息充足 | 降一级（如 T2→T1，T1→T0） |
| 上下文明显缺版本号/API签名/数据格式 | 升一级 |
| 关键事实用"应该是/大概"表述 | 升一级，并进入缺口检测 |

### 3. 风险面

| 风险 | 判定 |
|------|------|
| 涉版本兼容 / 生产环境 / 合规 / 真实数据 | T2 |
| 涉付费 API / 密钥 / 外部系统写入 | T2 |
| 涉许可证（开源复用 / 商用） | T2 |
| 纯本地、可回滚、影响面小 | 保持或降级 |

### 4. 用户明确意图

| 信号 | 判定 |
|------|------|
| 用户说"不用查""直接写""快点" | 降级或 T0，除非事实错误风险高 |
| 用户说"查一下""确认下""找找现有方案" | 升级，强制 Step 2 |

## 分级后流程对照

| 动作 | T0 | T1 | T2 |
|------|----|----|----|
| 缺口扫描 | — | 5 类快速过一遍 | 5 类 + 复查循环（≤2 轮） |
| 检索 | — | 仅高影响缺口 | 全部高影响 + 部分中影响 |
| 六维评分 | — | 快速判断 | 完整评分 |
| 冲突检测 | — | 外部 vs 原有假设 | 完整（含来源间矛盾） |
| trace | — | 简化 | 完整 |
| 复盘 | — | 一行 | 一行 |

## 出口条件（防过度流程）

- T1/T2 的 Step 1 若**无高影响缺口** → 立即退出 Skill，直接执行。
- 分级后若流程明显超出任务实际需要 → 主动降级，向用户说明。
- **流程是手段不是目的**：知止的价值是"轻任务不折腾、重任务不遗漏"，不是把所有任务都拖进流程。
